# Потоковый процессор

Потоковый процессор связывает загрузку данных с проверками и интерфейсом:

`ingestion → Kafka → stream processor → PostgreSQL → backend`.

Через Kafka приходит событие со ссылкой `raw_uri`. По этой ссылке процессор читает
строки из JSONL-файла в локальном хранилище (`file://`) или S3 (`s3://`).
Кроме загрузок данных, сервис обрабатывает события запуска и завершения пайплайнов:
`pipeline.started`, `pipeline.finished` и `pipeline.failed`.

## Запуск

Сначала установите зависимости проекта, включая дополнительные группы `kafka`,
`s3` и `storage`. Затем задайте `DATABASE_URL`, примените миграции и запустите процессор:

```sh
python -m alembic -c storage/postgres/alembic.ini upgrade head
python -m services.stream_processor --kafka localhost:9092 --quality-config config/quality
```

Адрес Kafka также можно передать через `KAFKA_BOOTSTRAP_SERVERS`, а группу
потребителей — через `KAFKA_GROUP_ID` (по умолчанию `stream-processor`).
Для доступа к S3 используются `S3_ENDPOINT_URL`, `S3_ACCESS_KEY` и `S3_SECRET_KEY`.

Пороги проверок задаются в YAML. Прежние переменные `QUALITY_MAX_*`
и `QUALITY_ROW_COUNT_*` больше не используются.

## Оценка загрузки

Обработчик `StreamEventHandler` выбирает конфигурацию по `dataset_id`.
Для таблицы без отдельного файла применяется `default_profile` из `defaults.yaml`.
Область проверки (`scope_id`) совпадает с идентификатором загрузки (`batch_id`).

До чтения исходных данных `EvaluationRunner` сохраняет план. Затем обработчик
вычисляет показатели и фиксирует наблюдения и ограничения, после чего запускает
проверки из плана. Если `raw_uri` отсутствует, сохраняются ошибка подготовки
и решение BLOCK. Если для первых загрузок ещё нет истории или эталона схемы,
пропуск фиксируется явно и по умолчанию приводит к WARN.

Попытки и результаты записываются по мере выполнения. После завершения результаты
и итоговое решение переносятся в таблицы, из которых читает backend, в одной
транзакции. Пока новая оценка выполняется, старое решение убирается из текущего
представления, но остаётся в истории.

Если проверка возвращает FAIL, публикуется событие `data.quality.failed`.
Пропуски и технические ошибки также видны в решении и истории, однако отдельного
Kafka-события для них пока нет.

## Повторы и восстановление

По умолчанию допускаются три попытки всего: первый запуск и два повтора с паузами
5 и 15 секунд. Для подготовки входных данных, каждой проверки и доставки
результатов число попыток учитывается отдельно.

Повторы предусмотрены для таймаутов, временных сетевых ошибок и определённых
временных ошибок S3 и транзакций PostgreSQL. Ошибки формата или конфигурации,
отсутствие локального файла, а также результаты FAIL и UNKNOWN не приводят
к автоматическому повтору.

Номер попытки сохраняется до её начала. Поэтому прерванная попытка тоже учитывается,
а после перезапуска доступны только оставшиеся попытки. Завершённые проверки
и уже подготовленные наблюдения повторно не вычисляются.
Исходные файлы загрузки должны оставаться неизменными; изменение метаданных
при том же `batch_id` отклоняется.

Если попытки подготовки или выполнения исчерпаны, сохраняется ERROR.
Для обязательной проверки это приводит к BLOCK. Если же недоступно хранилище
самой истории или не удалось доставить результат, обработчик выбрасывает
исключение и не подтверждает обработку сообщения в Kafka.
После исчерпания попыток доставки оператор должен разобраться с причиной
и явно запустить новую оценку. Внутри обработчика повторы ограничены.

Позиция прочитанного сообщения (offset) подтверждается после обработки.
Если сообщение приходит снова, система находит прежнюю оценку. При этом
блокировка PostgreSQL не позволяет одновременно обрабатывать одну загрузку.

Публикация уведомлений допускает повторную доставку (at-least-once): например,
процесс может остановиться сразу после отправки. Для одной пары
`evaluation_id` и `check_id` идентификатор `event_id` остаётся прежним,
поэтому получатель может использовать его для отсеивания дублей.

## Явная переоценка

Изменение YAML не запускает повторную проверку старых загрузок автоматически.
Чтобы проверить загрузку заново по текущим настройкам, укажите идентификатор
её существующей оценки и новый идентификатор запроса:

```sh
python -m services.stream_processor.reevaluate EVALUATION_ID --request-id review-2
```

Новый `request-id` создаёт отдельную оценку, а повтор команды с тем же
`request-id` продолжает уже созданную. Без `--kafka` команда сохраняет результат
только в БД; с `--kafka localhost:9092` она также отправляет уведомления.

Предыдущие оценки остаются в истории. Повторная доставка старого события
не заменяет более новую оценку в текущем представлении.
Получить идентификаторы оценок можно через метод репозитория
`QualityRepository.list_evaluations(dataset_id, scope_id)`.

## Тесты

```sh
python -m pytest tests/stream_processor tests/data_quality -q
```

Для PostgreSQL-тестов задайте `TEST_DATABASE_URL`, указывающую на отдельную
тестовую БД: эти тесты очищают её содержимое.
