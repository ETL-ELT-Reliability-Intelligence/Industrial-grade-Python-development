# Финальная версия и приёмка

Система мониторит качество, обнаруживает аномалии и предупреждает пользователя.
`BLOCK` — блокирующая оценка качества, а не команда остановки DAG. Инциденты, RCA,
VAE и расследующий агент остаются дальнейшим развитием.

## Воспроизводимый запуск

`python scripts/demo.py` использует синтетические CSV (seed=0, 300 заказов в месяц),
окна 0–3 и потери 60% платежей в последнем месяце. Для настоящего Olist используйте
`--mode olist --olist-dir data/olist --windows 16 17 18 19`. Наличие файлов,
периодов и непустых партий проверяется до старта. Другие окна могут изменить
статистический baseline: итоговый FAIL/WARN проверяется, а не обещается независимо
от данных. Синтетическая приёмка не требует скачивания Kaggle.

Каждый запуск создаёт новый Compose-проект, собственные тома и свободные локальные
порты. Скрипт печатает ссылки на интерфейс. API Airflow получает точный run_id:
queued/running означают ожидание; failed, неверная идентичность, исчезнувший запуск,
ошибка HTTP или некорректный ответ означают ошибку. Проверяется heartbeat scheduler.
Таймауты регулируются `--build-timeout`, `--start-timeout`, `--run-timeout` и
`--quality-timeout`; `RUN_TIMEOUT` поддерживается для совместимости.

После каждого DAG проверяются его сохранённый SUCCESS и четыре партии из
неизменяемых S3-манифестов текущего run_id. Сверяются число строк, завершение и
публикация оценки, API партий/оценок/запусков. В последнем месяце проверяются
row_count FAIL и policy WARN для order_payments. Старые результаты не участвуют
в подтверждении нового прогона. Манифест, состояния контейнеров, import errors
Airflow и последние логи находятся в `test-results/reliability-demo-*`.

`--recovery` дополнительно запускает реальные Kafka/S3/PostgreSQL-тесты в отдельной
`reliability_test` внутри созданного проекта. Проверяются смерть процесса после
сохранения результата до commit Kafka, потеря подключения к PostgreSQL и повтор
с новым подключением, недоступный брокер уведомлений и потеря подтверждения после
успешной публикации. Повторные уведомления имеют одинаковые event_id/dedup_key.
Затем PostgreSQL целиком временно останавливается: API должен вернуть 503, новая
партия публикуется в Kafka, после запуска БД её оценка должна завершиться ровно один
раз. Эти проверки не моделируют полную потерю диска или кластера.
`--cleanup` после диагностики удаляет только этот новый проект и его тома.

## Контейнеры и данные

Образы инфраструктуры закреплены digest. `infra/python/requirements.lock`
экспортируется из `uv.lock` с hashes. Airflow и dbt имеют отдельные окружения и
полные lock-файлы; Airflow runtime изолирован также от лишних провайдеров базового
образа. При обновлении: `uv export --locked --no-emit-project --extra storage
--extra kafka --extra s3 --extra ml --extra dev --format requirements-txt
--output-file infra/python/requirements.lock`; Airflow/dbt — `uv pip compile`
соответствующего `.in` с `--python-version 3.11 --python-platform linux --generate-hashes`.
Изменённые lock-файлы требуют повторной сборки и приёмки.

Kafka проходит healthcheck. Одноразовый `infrastructure-init` проверяет доступ к S3
записью/чтением и условным созданием объекта, создаёт все контрактные топики
идемпотентно; потребитель и scheduler ждут его успешного завершения. Автосоздание
топиков отключено. Временные ошибки во время обработки не подтверждают Kafka-offset;
перезапуск и сохранённые бюджеты попыток позволяют возобновить обработку либо
оставляют явную ошибку для расследования.

Raw-файлы создаются исключительно: локально атомарной публикацией полного файла,
в S3 — PutObject с If-None-Match. Коллизии номеров имеют ограниченный бюджет повторов.
Первый завершённый манифест run_id неизменяем; все конкурирующие вызовы читают и
возвращают его результат. Проигравший вызов или сбой до commit может оставить
осиротевший raw-файл, который не публикуется и не заменяет данные победителя.
Автоматическое удаление таких файлов не выполняется. История схем защищена OS-lock
локально и сравнением ETag в S3. Хранилище должно поддерживать условные записи:
[контракт S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

Миграция 0006 добавляет сохранённые результаты статистического детектора и историю
попыток обучения. Она не удаляет прежние данные. Миграция 0003, если ещё не применена,
удаляет старые результаты качества: обновляйте существующую БД после резервного
копирования; для восстановления прежней схемы нужен backup. Новое демо всегда
использует собственную БД и применяет всю цепочку миграций.

## Интерфейс и ML

Выберите dataset → область проверки → расчёт. Раздел «Аномалии и прогноз объёма»
показывает статистические измерения и ML отдельно: факт, ожидание, границы, статус,
причину пропуска/ошибки, версию и связанные аномалии. Отсутствующая запись обозначается
SKIPPED/not_recorded, а не PASS; для неподходящего источника — not_applicable.
API: `GET /api/v1/datasets/{dataset_id}/evaluations/{evaluation_id}/detections`.
Владение оценкой проверяется до чтения детекторов.

Для просмотра почасового сценария после запуска сервисов:
`docker compose -p ИМЯ_ПРОЕКТА exec -e KAFKA_BOOTSTRAP_SERVERS=kafka:19092 backend python -m scripts.seed_volume_demo`.
Это явно синтетическая история с согласованным received_at. Она обучает модель
и публикует три партии mock_orders: нормальную, всплеск и нехватку истории лагов.

Диагностика обучения сохраняет число пригодных целевых часов из 504, отсутствующие
периоды и лаги, cutoff и последнее успешное обучение. Строгое требование истории
сохранено; пропущенные часы не заменяются нулями, PASS не используется как метка нормы.
Последняя попытка обучения показывается в UI независимо от выбранной старой оценки.

Эксперимент: `python -m services.ml.benchmark --seed 42 --output reports/ml`.
Он сравнивает бустинг, медиану и прошлую неделю, разделяя обучение, калибровку и тест
по времени. Отчёт содержит precision/recall, ложные тревоги, задержки, покрытие и
ширину интервалов. [Результаты и ограничения](../reports/ml/README.md): загрязнение
калибровки может сделать интервал настолько широким, что новые нарушения не видны.
Это ограничение модели, а не доказательство нормальности данных.
