# Профили партий

После существующих проверок stream processor накапливает независимые статистические
признаки. Этот расчёт не меняет решение PASS/WARN/BLOCK и не публикует события аномалий.
[Регрессия объёма заказов](order_volume.md) выполняется отдельно в том же обработчике
и использует почасовые наблюдения из dataset_profiles.

## Определение признаков

`config/features.json` задаёт фиксированные колонки и словари отдельно от конфигурации
проверок качества. `--feature-config PATH` позволяет выбрать другой файл при запуске
processor или переоценке. Для датасета без определения сохраняется только объём партии.
Колонки в определении перечисляются по имени в отсортированном порядке. Неизвестные
колонки не расширяют набор признаков автоматически.

Каждый профиль содержит полное определение и его SHA-256, а также отдельный отпечаток
реализации: исходного кода расчёта и контрактов признаков. Изменение порога проверки
качества не меняет определение признаков. Сопоставлять профили можно только при
совпадении датасета, источника, гранулярности, версии схемы, определения и реализации.
Полнота периода хранится явно. Повтор одного периода не является новым независимым
наблюдением; будущий отбор обучающей выборки должен учитывать это.
Время поступления `received_at` сохраняется и для партий без границ периода.

Статистики первой версии:

- Объём партии; количество пропусков и непустых значений; количество и доля уникальных
  непустых значений. Уникальность определяется по каноническому JSON: строка `"1"` и
  число `1` различаются. Отсутствующее поле считается пропуском; отсутствие колонки
  во всех строках отмечается отдельно. Пустая строка не считается пропуском.
- Для явно выбранных числовых колонок: минимум, максимум, среднее, стандартное
  отклонение с `ddof=0`, квантили (по умолчанию 0.25, 0.5, 0.75). Вычисления используют
  только успешно преобразованные конечные числа, представимые конечным float.
  Boolean, структуры, некорректные строки, NaN и бесконечности исключаются.
  Рядом хранятся `valid_count`, `null_count`, `parse_error_count`.
- Квантили: линейная интерполяция между соседними элементами отсортированной выборки
  в позиции `(n - 1) * q`. Decimal-арифметика использует фиксированную точность 50
  и округление ROUND_HALF_EVEN независимо от внешнего контекста.
  Итоговые числовые характеристики сохраняются как float. При отсутствии корректных
  чисел характеристики равны null; для одного числа стандартное отклонение равно 0.
- Категориальные частоты: фиксированный упорядоченный словарь строк и отдельная корзина
  «прочие». Знаменатель — число непустых значений. Нестроковые значения попадают в
  «прочие». При пустой выборке счётчики равны нулю, доли — null.

Нарушения правил не входят в признаки. Идентификаторы и почтовые коды автоматически
в числа не преобразуются. Тесты требуют точного совпадения счётчиков при перестановке
строк и допуска `rel=1e-12`, `abs=1e-12` для вещественных характеристик.

## Исходные данные и хранение

SHA-256 рассчитывается по точным байтам того же чтения raw, которое используется для
проверок и профиля. Контрольная сумма сохраняется также в новой оценке качества.
Повтор завершённой оценки переиспользует её результаты, но повторно читает raw для
проверки идентичности и накопления признаков. Изменение даже форматирования JSONL
меняет контрольную сумму. Изменённое содержимое под прежним `batch_id` получает
технический статус CONFLICT; старый профиль не заменяется. Исправленные данные нужно
загрузить как новую партию с новым `batch_id` — это идентификатор ревизии в этой итерации.

Миграция `0004` добавляет таблицы, сохраняя существующие данные:

- `feature_inputs` закрепляет контрольную сумму за датасетом и партией.
- `feature_profiles` содержит только успешные неизменяемые снимки. UNIQUE по
  `(dataset_id, batch_id, raw_sha256, definition_hash, implementation_version)`
  обеспечивает один успешный профиль, в том числе при конкурентной записи.
  UPDATE снимков и идентичности входа запрещён триггерами БД.
- `feature_profile_evaluations` связывает снимок с оценкой качества и хранит `eligible`.
  Одна оценка может иметь несколько версий расчёта; один профиль — несколько оценок.
  Изменение порогов создаёт новую оценку со своей пригодностью, но использует прежний профиль.
- `profiling_attempts` отдельно хранит RUNNING / COMPLETED / ERROR / CONFLICT,
  время, идентификаторы расчёта и описание ошибки. Неудачная или прерванная попытка
  не препятствует следующей; успешный профиль переиспользуется.

Существующие `dataset_profiles` остаются рабочими сводками статистических проверок
с прежним жизненным циклом и прежним допуском в эталон. Это отдельные данные, не
стабильные признаки для будущей модели. В `feature_profiles` поля `eligible` нет.
Пригодность для статистического эталона не является меткой «норма» для обучения ML.

Ошибка дополнительного расчёта сохраняется как ERROR после сохранения и доставки
решения качества. Если недоступна сама БД, ошибка хранения передаётся обработчику
доставки для повтора события; уже сохранённое решение качества не пересчитывается.
При аварийном прерывании попытка может остаться RUNNING, следующая обработка создаёт
новую попытку. Старые оценки без контрольной суммы не получают её задним числом:
для них фиксируется доступный на момент профилирования raw.

## Применение и повторный расчёт

При настроенной `DATABASE_URL` применить миграции до запуска обновлённого processor:

```sh
python -m alembic -c storage/postgres/alembic.ini upgrade head
```

Повтор доставки события повторяет только незавершённую работу и накопление признаков.
Для отдельного повторного расчёта без новой оценки качества и публикации событий:

```sh
python -m services.stream_processor.reprofile EVALUATION_ID
python -m services.stream_processor.reprofile EVALUATION_ID --feature-config config/features.json
```

Код возврата 0 означает успешное накопление или переиспользование профиля; 1 —
ошибку расчёта либо конфликт. После изменения определения или реализации сохраняется
новая версия профиля. Команд просмотра, экспорта и отчётов о накоплении в этой итерации нет.

Проверка:

```sh
python -m pytest tests/stream_processor tests/contracts tests/data_quality tests/storage -q
```

Тесты PostgreSQL, включая конкурентную запись и ограничения БД, требуют отдельной
`TEST_DATABASE_URL`; тестовая БД очищается. Обычные тесты не требуют PostgreSQL.
