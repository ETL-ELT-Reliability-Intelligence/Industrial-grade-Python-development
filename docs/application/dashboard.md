# Dataset dashboard

Запуск backend и БД описан в [README](README.md). Экран доступен на `/`, все данные
получает через `/api/v1`; frontend не обращается к PostgreSQL или Kafka напрямую.
Никакой сборки или Node.js для запуска не требуется.

Основа оформления — исходный CSS и компоновка demo из коммита `5d304bf`,
а не новая сетка карточек: слева список, справа единая карточка с внутренними
разделами; сохранены пропорции колонок, отступы, Tahoma, серая палитра
Windows Classic/XP, синие заголовки и объёмные кнопки. Добавлены только стили
специфичных для datasets элементов (пагинация, evidence, статусы качества).

Текущий dataset-экран выбран рабочим вариантом; прежний incident demo сохранён
отдельно и не заменяет его. Локальный просмотр: dataset dashboard на порту 8000,
старое demo на 8001 (команды запуска в README). Эксперименты с оформлением
планируются в `feature/design-metamarphoses`, ответвлённой от API-коммита;
они не задерживают второй коммит dashboard и PR текущей ветки.

## Сценарий

1. Выбрать dataset в каталоге. Для явного seed: `sample-app-orders`.
2. Посмотреть загрузки, число строк, received_at и номер schema version.
3. Независимо выбрать scope, например `sample-window-1`.
4. Сопоставить наблюдение, ограничение, статус и диагностику каждой проверки.
5. Отдельно посмотреть сохранённое решение policy, причины и decided_at.
6. Обновить данные после записи upstream. Кнопка обновляет все видимые разделы.

`/?dataset=sample-app-orders&scope=sample-window-1` — прямая ссылка. История браузера
восстанавливает выбранные dataset/scope. Списки имеют пагинацию по 50 записей;
переход на новый dataset сбрасывает страницы batches/scopes и выбранный scope.
После первого открытия область автоматически не выбирается.

На экране различаются загрузка, отсутствие данных, отсутствие измерения/решения,
404 и недоступность API/БД. В каждом ошибочном разделе есть повтор запроса.
Новые запросы отменяют старые, а проверка актуальности защищает от запоздавшего
ответа. После ошибки старые факты не отображаются как успешно обновлённые.

Время последнего успешного ответа API — техническое время загрузки экрана,
не watermark платформы. Времена проверок/решений подписаны отдельно.
PASS/FAIL/UNKNOWN относятся к проверкам; PASS/WARN/BLOCK — к policy.
Нулевое значение отображается как 0, отсутствующее — как «Нет значения».
Нет вычисляемого frontend «общего здоровья dataset».

## Проверки

```powershell
node --check services/frontend/app.js
.venv/Scripts/python.exe -m pytest tests/application/test_dashboard.py -q
```

Браузерные сценарии идут через настоящий ASGI API. Отдельный сценарий с
`TEST_DATABASE_URL` записывает проверки через storage и проверяет появление
нового решения после обновления страницы. Остальные сценарии используют
явный test double для ошибок, пустых состояний и контролируемых задержек.

Проверяются пагинация всех трёх списков, прямые ссылки и Back, retry, гонка
ответов, управление клавиатурой, мобильная ширина и безопасный вывод текста.
Историческое demo имеет отдельные браузерные тесты.
