# Datasets, качество и запуски pipelines

Запуск backend и БД описан в [README](README.md). Экран доступен на `/`, все данные
получает через `/api/v1`; frontend не обращается к PostgreSQL или Kafka напрямую.
Никакой сборки или Node.js для запуска не требуется.

Основа оформления — исходный CSS и компоновка demo из коммита `5d304bf`,
а не новая сетка карточек: слева список, справа единая карточка с внутренними
разделами; сохранены пропорции колонок, отступы, Tahoma, серая палитра
Windows Classic/XP, синие заголовки и объёмные кнопки. Добавлены только стили
специфичных для datasets элементов (пагинация, evidence, статусы качества).

Dataset-экран поддерживает три оформления: исходный Windows XP / Classic,
серверы CS 1.6 и Design Wizard. Classic остаётся вариантом по умолчанию.
Переключатель находится в верхней панели. Все темы работают на одном frontend
и одном API; смена оформления не перезагружает данные и не сбрасывает пагинацию.
В Wizard можно скрыть статичную панель помощника. Остальные дизайн-концепции удалены.

Прежний incident demo сохранён отдельно. Локальный просмотр: dataset dashboard
на 8000, старое demo на 8001. Поведение параметра `theme` — в [описании тем](themes.md).

## Сценарий

1. Выбрать dataset в каталоге. Для явного seed: `sample-app-orders`.
2. Посмотреть загрузки, число строк, received_at и номер schema version.
3. Независимо выбрать scope, например `sample-window-1`.
4. Посмотреть историю расчётов. При первом открытии автоматически выбирается
   новейший расчёт; scope по-прежнему выбирается отдельно от batch.
5. Выбрать прошлый расчёт и сопоставить выполнение, результат проверок и policy.
6. Раскрыть наблюдения, ограничения, эталон, конфигурацию и историю попыток.
7. Обновить данные после записи upstream. Выбранный расчёт сохраняется.

`/?dataset=orders&scope=window-1&evaluation=EVALUATION_ID` — прямая ссылка.
Явный evaluation имеет приоритет. Автоматический выбор записывается через
replaceState; ручной — через pushState. История браузера восстанавливает выбор.
Списки имеют пагинацию по 50 записей. Смена dataset сбрасывает страницы
batches/scopes; смена dataset или scope сбрасывает расчёт и страницу его истории.
Переход между страницами истории сохраняет открытый расчёт, даже если его
строка находится на другой странице. Переключение темы не вызывает запросов.

Если история успешно прочитана и пуста, показывается прежний результат /quality
с пояснением об отсутствии истории. Это поддерживает явный seed sample-app-orders.
Ошибка истории, пустой ID расчёта, неизвестный расчёт или ссылка на расчёт другого
scope показываются как ошибка с повтором; старый результат автоматически не подставляется.
Обновление ручное, фонового опроса нет.

Можно добавить `&theme=classic`, `&theme=cs` или `&theme=wizard`. Явная тема в ссылке
приоритетнее сохранённой настройки браузера. Смена датасета сохраняет оформление.

На экране различаются загрузка, отсутствие данных, отсутствие измерения/решения,
404 и недоступность API/БД. В каждом ошибочном разделе есть повтор запроса.
Новые запросы отменяют старые, а проверка актуальности защищает от запоздавшего
ответа. После ошибки старые факты не отображаются как успешно обновлённые.

Время последнего успешного ответа API — техническое время загрузки экрана,
не watermark платформы. Времена проверок/решений подписаны отдельно.
PENDING/RUNNING/COMPLETED/SKIPPED/ERROR относятся к выполнению;
PASS/FAIL/UNKNOWN — к соответствию данных; PASS/WARN/BLOCK — к policy.
COMPLETED может сопровождаться BLOCK. Отсутствующий результат не становится UNKNOWN.
Подготовка наблюдений и публикация показываются отдельно. evaluated_at — время
оценки по контракту producer, не время завершения. updated_at относится к записи
расчёта, а времена попыток — к конкретным попыткам.
Нулевое значение отображается как 0, отсутствующее — как «Нет значения».
Нет вычисляемого frontend «общего здоровья dataset».

## Конфигурация и читаемость загрузок

«Конфигурация расчёта» показывает общую сводку, настройки повторов и таблицу
проверок. В каждой строке видны ключ и тип проверки, колонка, сохранённые параметры,
реакции на FAIL и UNKNOWN. «Свойства» раскрывают обязательность, версию реализации
и реакции при недостатке истории или отсутствии схемы. Поля схемы выводятся
таблицей, простые массивы — компактным списком значений внутри ячейки.
Параметры не дополняются вычисленными frontend значениями; нули, false и точность
малых чисел сохраняются. Неизвестные составные поля доступны отдельно как текст.

В загрузках Batch ID и число строк не разрываются; дата и время разделены на две
читаемые строки. Узкая колонка «Схема» содержит номер версии, её полная подпись —
«Версия схемы». URI источника виден полностью с переносами на границах пути.
Очень длинные сегменты могут переноситься внутри ячейки. На узком экране таблицы
прокручиваются внутри панелей, а не сжимают идентификаторы и числа.

В Design Wizard загрузки и области качества занимают всю ширину правой панели.
На ширине до 1000 px каталог располагается над карточкой dataset.

## Проверки

Подготовьте окружение по [инструкции приложения](README.md#установка-и-запуск).

```powershell
node --check services/frontend/app.js
node --check services/frontend/themes.js
uv run --no-sync python -m pytest tests/application/test_dashboard.py -q
```

Браузерные сценарии идут через настоящий ASGI API. Отдельный сценарий с
`TEST_DATABASE_URL` записывает проверки через storage и проверяет появление
нового решения после обновления страницы. Остальные сценарии используют
явный test double для ошибок, пустых состояний и контролируемых задержек.

Во всех трёх темах проверяются пагинация всех списков, прямые ссылки и Back, retry,
гонка ответов, управление клавиатурой, мобильная ширина и безопасный вывод текста.
Дополнительно проверяются сохранение оформления, приоритет URL, недоступное
localStorage и переключение темы без запросов API и сброса текущей страницы списка.
Историческое demo имеет отдельные браузерные тесты.

Регрессия читаемости проверяет загрузки на ширинах 1440, 1280, 1024, 900, 768
и 390 px: ID и числа остаются целыми, длинные значения доступны в прокручиваемой
таблице. Для конфигурации проверяются шесть видов проверок, раскрытие свойств
клавиатурой, нули и false, точность дробных параметров, отсутствие подставленных
defaults и безопасный вывод произвольного текста. Сценарии общие для трёх тем.

## Организация frontend

ES-модули работают без сборки. ApiClient отвечает за HTTP и сообщения ошибок;
EvaluationController — за выбор, пагинацию, отмену запросов и переход к legacy;
QualityView — только за DOM. Зависимости передаются контроллеру при создании.
configurationView формирует таблицу сохранённой конфигурации; её стили отделены
в configuration-view.css и используют общую палитру темы.
Общие функции вывода текста, таблиц и значений находятся в ui.js.
app.js связывает эти части с существующим каталогом и выбором dataset/scope.
Динамические данные выводятся через textContent, HTML из результатов не исполняется.

Новые браузерные сценарии находятся в существующем test_dashboard.py, поэтому
продолжают запускаться в общем CI. Тест PostgreSQL изменяет исполнение через
PostgresQualityRepository и проверяет появление изменения после обновления экрана.
Тестовые фикстуры не используются приложением при запуске.

## История запусков pipelines

Пункт «Запуски pipelines» открывает `/pipelines`. Слева — пагинированный каталог
pipelines с сохранёнными запусками, справа — история выбранного pipeline:
run ID, RUNNING/SUCCESS/FAILED, начало, завершение и сохранённая ошибка.
Для выполняющегося запуска завершение обозначено «Ещё выполняется».
Отсутствующая ошибка выводится как «Не указана».

Прямая ссылка: `/pipelines?pipeline=orders%2Fdaily`. Выбор хранится в URL;
Back/Forward восстанавливают его. Списки имеют независимые страницы по 50 записей;
выбор другого pipeline сбрасывает страницу запусков. Ручное обновление сохраняет
выбор и страницы. Переход между разделами сохраняет оформление, смена темы
не вызывает запросов API. Данные pipelines не смешиваются с выбором dataset.

Пустой каталог, неизвестный pipeline, загрузка и ошибка различаются; сбой запроса
не маскируется пустой историей. Есть повтор запроса и защита от запоздалого ответа.
Ошибки и идентификаторы выводятся как текст. На узком экране таблица прокручивается
внутри раздела. SUCCESS описывает выполнение pipeline; качество смотрят отдельно.

Сценарии в существующем `test_dashboard.py` проверяют навигацию, темы, пагинацию,
retry, прямые ссылки, гонку ответов, мобильную ширину и безопасный вывод текста.
Сценарий PostgreSQL сохраняет RUNNING через общий storage, затем FAILED с ошибкой
и проверяет обновление API/UI. Запуск реального Airflow/Kafka этим тестом не покрыт.
