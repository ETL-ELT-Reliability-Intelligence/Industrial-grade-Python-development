# Итерация application-layer: datasets и качество

Зона ответственности — backend/frontend. Опора — текущие общие контракты,
PostgreSQL-схема и storage-репозитории. Старый incident demo изолирован и не
задаёт архитектуру реального приложения.

В этой итерации считаем коллег недоступными: не ждём ответов для реализации
доступного сценария. Это ограничение текущего дня, а не правило дальнейшей
работы. В следующих итерациях согласовываем контракты и просим владельцев
компонентов реализовывать недостающие зависимости в их зоне ответственности.

## Два результата

1. `feat: add PostgreSQL dataset and quality query API` — отдельное историческое
   demo, реальный read API, зависимости, тестовое наполнение, HTTP/PostgreSQL-тесты,
   документация backend.
2. `feat: add dataset and quality dashboard` — frontend без сборки, выбор dataset
   и scope, batches/проверки/policy, пагинация, состояния ошибок/пустоты,
   браузерные проверки и итоговые договорённости/следующие работы.

Критерий: записанные через storage данные видны через HTTP и браузер, изменение
policy появляется после обновления, недоступность БД не маскируется demo.

## Разделение дальнейшей работы

Сразу после первого коммита создать `feature/design-metamarphoses` на его HEAD,
оставаясь в `feature/application-layer#2`. Затем независимо сделать второй коммит
с текущим dataset dashboard в исходной ветке и открыть PR. Design-ветка не блокирует
этот PR; перенос dashboard-коммита для экспериментов и выбор будущего оформления
выполняются позже. Рабочий экран — текущий dataset dashboard; старое incident demo
сохраняется отдельным запуском. Коммиты пользователь делает сам.

## Не включено

Не реализуем ingestion consumer, вычисление статистик, quality policy в runtime,
метрики, pipelines, инциденты, lineage, RCA, Agent, авторизацию или изменение
бизнес-данных через API. Seed — только явное тестовое наполнение.

## После реализации

К frontend-коммиту прилагается `dashboard.md` — сценарий экрана и проверок.
Рабочие заметки по договорённостям, дальнейшим задачам и подготовке коммитов
хранятся локально и не входят в репозиторий. Договорённости помечаются как
предложения, пока владельцы не подтвердили их. Пользователь сам выполняет
коммиты и открывает PR; сообщения коллегам автоматически не отправляются.
