# План уровня приложения

Область: `services/backend` и `services/frontend`. Документация участника, отвечающего за уровень приложения; общие схемы системы находятся на уровень выше, в `docs/`.

Первая итерация: согласовать направление и получить работающий путь от API до экрана. План основан на предоставленном `ARCHITECTURE.md`; ниже описана только область backend/frontend. Это предложение для команды, а не уже согласованный контракт соседних компонентов.

## Границы ответственности

Пользователь приложения — инженер data-платформы. Он должен увидеть проблему, открыть инцидент и понять, какие наблюдения его подтверждают и какие потребители могут быть затронуты.

| Часть | Твоя ответственность | Что приходит от других компонентов |
| --- | --- | --- |
| Backend | HTTP API, валидация запросов, представление данных, обработка ошибок, позднее оркестрация investigation | Инциденты, аномалии, метрики, pipeline runs, lineage, кандидаты причин и impact |
| Frontend | Обзор состояния, список/карточка инцидента, dataset и lineage, состояния загрузки и ошибок | Только ответы backend API |
| Интеграция | Согласовать формат чтения и обновления данных, freshness и поведение при недоступности источников | Схема PostgreSQL/read model и примеры от владельцев storage и Incident Engine |

Backend не вычисляет аномалии, RCA и blast radius. Frontend не обращается к Kafka, PostgreSQL и ML-сервисам. В архитектуре участнику №4 также назначены Incident Intelligence и Agent, но этот план не расширяет твою заявленную область за пределы backend/frontend.

## Как строить

Начать с одного backend на Python/FastAPI и одного frontend. На первой итерации frontend — HTML/CSS/JavaScript без сборки; выбор React/Vue/другого фреймворка оставляем до появления более сложной навигации и состояния. Это позволяет сначала проверить пользовательский сценарий.

Поток: источник готовых данных → repository → FastAPI → HTTP/JSON → dashboard. В первой версии repository возвращает демонстрационные данные. Позже адаптер PostgreSQL заменит его без изменения экранов и публичного API. Backend также раздаёт frontend, поэтому локально достаточно одного процесса.

## Итерации

| Итерация | Backend | Frontend | Проверяемый результат |
| --- | --- | --- | --- |
| 1. Работающий сценарий | Health, обзор, список и карточка инцидента; типизированные ответы; demo repository; OpenAPI | Счётчики, фильтр статуса, список и карточка; loading/empty/error/retry | После одного локального запуска можно открыть инцидент и увидеть наблюдения, кандидата причины и impact; demo явно обозначено |
| 2. Реальные данные | Согласованный read model PostgreSQL, конфигурация окружения, пагинация и сортировка, интеграционные проверки | Данные из той же API-модели; дата актуальности и ручное обновление | Изменение upstream-данных появляется на экране; недоступность источника видна как ошибка |
| 3. Dataset и pipelines | Dataset details, статистика и pipeline runs; временные диапазоны | Карточка dataset, история метрик и запусков, ссылки из инцидента | Можно проверить, что происходило с конкретными данными и их обработкой |
| 4. Lineage и impact | Готовый граф от Lineage Engine и impact от Incident Engine; признак полноты графа | Граф зависимостей, выделение затронутых узлов, timeline | Пользователь отличает наблюдаемую проблему от потенциального downstream-влияния |
| 5. Investigation | Адаптер Agent, асинхронный job/status API, timeout, структурированные evidence | Запуск расследования, прогресс, результат со ссылками на evidence | Результат расследования объясним, ошибка Agent не ломает просмотр инцидента |
| 6. Готовность к командной эксплуатации | Auth/RBAC, аудит изменений, метрики/логи, проверка конфигурации, CI и deployment | Доступ по ролям, адаптивность, доступность, проверка основных сценариев в браузере | Команда может безопасно пользоваться приложением с реальными данными |

Это итерации приложения: они не требуют реализовать самостоятельно все предыдущие слои платформы. Пока upstream ещё не готов, экран и API развиваются на фиксированных примерах. Auth следует перенести раньше, если реальными данными нужно делиться за пределами локальной среды.

## Два коммита первой сессии

1. `doc: define application scope and iteration roadmap` — этот план, границы ответственности, зависимости и критерии готовности.
2. `feat: add demo incident API and dashboard` — запускаемый FastAPI, frontend, демонстрационный сценарий, API/UI-проверки и инструкция запуска.

## Чек-лист первой итерации

- Один запуск открывает dashboard и `/docs`; инфраструктура Kafka/Airflow/БД не требуется.
- Frontend получает все данные через `/api/v1`, без копии бизнес-данных в JavaScript.
- Фильтр показывает открытые/закрытые инциденты; карточка открывается по стабильному ID.
- Неизвестный инцидент даёт 404; неверный фильтр — 422; ошибка API имеет видимое состояние и повтор загрузки.
- Пустой список не выглядит как сбой; loading и demo-режим явно обозначены.
- Кандидат причины обозначен как гипотеза; score не называется вероятностью доказанной причины.
- Проверены API, связь overview/list/detail и загрузка frontend-файлов; результат зафиксирован в коммите.
