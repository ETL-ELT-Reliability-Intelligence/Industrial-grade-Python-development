# Application-layer #5: история запусков pipelines

Зона ответственности — backend и frontend. Ветка `feature/application-layer#5`
создана от `origin/main` (`ed08599`, после PR #18–21). PR #20 с историей качества
уже объединён; предыдущая ветка `feature/application-layer#4` сохранена.

## Результат итерации

Каталог pipelines и история запусков доступны через API и отдельный экран
`/pipelines`: пагинация, исходный статус, времена начала/завершения, ошибка,
прямая ссылка на pipeline и ручное обновление. Сохраняются три оформления.

Вход — общий `PipelineRun` и существующая таблица `pipeline_runs`; каталог и
offset-пагинация реализованы в application read-адаптере. Контракты, общий storage
и миграции коллег не изменяются. Pipeline выбирается отдельно от dataset:
в контракте нет подтверждённой связи между ними.

Критерий: запуск, сохранённый через `PostgresPipelineRunRepository`, читается API
и браузером; переход RUNNING → FAILED с ошибкой виден после ручного обновления.
Успешное выполнение pipeline не считается успешной проверкой качества.

История расчётов качества из итерации #4 остаётся доступна на основном экране.

## Следующие шаги

   в воспроизводимом сценарии команды; исправить мониторинг и готовность topics.
   Связь запуска с dataset отдельно согласовать, не выводить её из похожих ID.
2. История метрик dataset. Вход — MetricPoint, профили и существующие
   методы чтения. Результат — история выбранной метрики/колонки с корректными
   версиями статистики, временами и отсутствующими значениями.
3. По ответам quality/storage: уточнить ход выполнения и времена. Вход — подтверждённые
   контракты из таблицы выше. Результат — UI показывает новые поля без собственных догадок.
4. После готовности Incident Intelligence: API и экраны инцидентов, lineage, RCA и
   impact. Вход — рабочие контракты, read-методы и сохраняемые примеры. Результат —
   реальный инцидент и его связи читаются через приложение. Старое demo контрактом не является.

В этой итерации нет запуска или перезапуска DAG из UI, запуска переоценки через API,
редактирования конфигурации, изменения алгоритмов качества, метрик, pipelines,
инцидентов, lineage или Agent.
Коммиты и PR создаёт пользователь. Внутренние commits.md и handoff.md не включаются.

## Проверки итерации #5

Локально: PostgreSQL 18 в новом изолированном тестовом кластере, Edge headless.
Полный набор `tests/application`: **175 passed без пропусков** с
`CI_REQUIRE_NO_SKIPS=1`. Проверены HTTP-контракты, SQL-пагинация и параметры,
снимок чтения, readiness при отсутствии таблицы и обновление запуска через общий
storage. Браузерные проверки включают прямые ссылки, Back/Forward, ручное обновление,
retry, запоздалый ответ, безопасный текст, три оформления и ширину 390 px.

После обновления upstream отдельно прошли **405 tests и 104 subtests** контрактов,
quality, ingestion, pipelines и stream processor без внешних сервисов.
Ruff по репозиторию, форматирование Python приложения, синтаксис новых JavaScript
и `git diff --check` прошли. Визуально проверены desktop/mobile всех трёх тем;
скриншоты находятся в игнорируемом `test-results/pipelines/`.

Удалённый CI не запускался. Тесты PostgreSQL выполнялись на одноразовой
`application_iteration5_test` (PostgreSQL 18); существующие БД не мигрировались.

## Реальный Olist-прогон 08.11.2026

Официальный архив Kaggle `olistbr/brazilian-ecommerce` скачан и проверен (ZIP CRC,
SHA256); все девять CSV находятся в игнорируемой `data/olist`, происхождение —
`data/olist/SOURCE.json`. В архиве 99 441 заказ. В приложение загружен отдельный
сценарий за февраль–май 2018 года (окна 16–19); первые месяцы набора почти пусты.

Создан отдельный Compose project `ri-olist-demo` с собственными томами,
PostgreSQL 16 на порту 5433 и миграциями до 0004. Четыре DAG `olist_ingestion`
завершились успешно, выполнены `dbt run` и `dbt test`. Через Kafka сохранены
16 загрузок, завершённые Evaluation, решения policy и четыре SUCCESS запуска.

В четвёртом запуске намеренно сохранено 40% платежей: **7 135 → 2 854**.
