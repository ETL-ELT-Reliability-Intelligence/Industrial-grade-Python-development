# Архитектура backend уровня приложения

Область: `services/backend`. Текущая версия читает готовые инциденты; обнаружение аномалий, RCA и вычисление impact остаются за владельцами соответствующих компонентов.

## Структура первой итерации

```text
Frontend / будущие Agent tools
          │ HTTP / JSON
          ▼
api.py                 маршруты, валидация, HTTP-ошибки
          │
          ▼
queries.py             сценарии чтения, фильтр, сборка обзора
          │ IncidentRepository (Protocol)
          ▼
repository.py          DemoIncidentRepository → demo.json

models.py              типизированные ответы API
main.py                create_app(), выбор адаптера, подключение router и frontend
```

HTTP-обработчики делегируют работу `IncidentQueries`. Query-слой не зависит от FastAPI и не знает о JSON-файле. Repository не формирует HTTP-ответы. `create_app(repository=...)` позволяет подставить другой адаптер и проверить те же сценарии без запуска инфраструктуры.

`models.py` содержит модели начального read model и публичного API. В первой итерации они общие, поскольку преобразование между двумя одинаковыми моделями не требуется. ORM-модели при подключении БД должны оставаться внутри адаптера: frontend получает документированные API-модели, а не строки таблиц.

## Как развивать

| Следующая потребность | Место изменения |
| --- | --- |
| Чтение реальных инцидентов | PostgreSQL-адаптер `IncidentRepository`, выбор в `create_app` |
| Конфигурация подключения | Отдельный settings-модуль, загрузка при старте; секреты из окружения |
| Connection pool и завершение работы | Lifespan приложения; сессия БД на запрос через dependency, без общей session на все запросы |
| Пагинация и фильтрация больших списков | Параметры HTTP и query-слоя; фильтр/сортировка/limit в запросе БД, overview отдельной агрегацией |
| Dataset, pipeline runs, lineage | Отдельные routers и queries по мере появления сценариев; соответствующие read adapters |
| Изменение статуса инцидента | Отдельный command-сценарий с правилами переходов, правами, транзакцией и аудитом |
| Investigation | Адаптер Agent и отдельный job/status API; длительную работу не выполнять внутри GET или HTTP-запроса на запуск |
| Недоступность источника | Перевод ошибок адаптера в HTTP 503 в API-слое, логирование; не выдавать demo как реальные данные |

Пока нет PostgreSQL, команды изменения состояния, Agent, пагинации и settings. Текущий repository синхронный; HTTP-обработчики объявлены через `def`. При выборе async-драйвера потребуется согласованно изменить интерфейс repository, queries и обработчики — нельзя просто вызвать блокирующий драйвер внутри `async def`.

Обзор сейчас рассчитан на небольшой demo-набор. В реальной версии источник обязан определить время актуальности и согласованность снимка для overview/list/detail. `snapshot_at` не заменяет readiness-проверку и не доказывает, что данные свежие.

## Правила развития контракта

- Все URL приложения находятся под `/api/v1`; ID приходят от владельца данных.
- Статусы и severity типизированы. Их смысл нужно согласовать с Incident Engine до интеграции.
- Время передаётся с UTC offset; UI переводит его в локальный часовой пояс.
- Подтверждённые наблюдения и потенциальное влияние имеют разные поля; RCA score обозначает ранжирование гипотез.
- В ответы явно передаётся `data_mode`; у моделей нет автоматического значения `demo`.
- Сохранение совместимости проверяется существующими API- и браузерными сценариями при замене адаптера.

Frontend пока использует простой CSS в духе Windows XP и административных веб-страниц начала 2000-х. Основная цель итерации — проверить API и пользовательский сценарий; визуальное оформление развивается позднее.
