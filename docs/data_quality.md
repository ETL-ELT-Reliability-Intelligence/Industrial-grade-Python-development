# Проверки качества

Библиотека `data_quality` сравнивает измеренные показатели с заданными ограничениями.
Например, она проверяет, достаточно ли строк в загрузке. Все значения передаёт
вызывающий код: функции не обращаются к БД, файлам или системным часам.
Контракты проверяют структуру данных, а статус вычисляет сама функция проверки.

## От настроек до решения

1. Сначала система объединяет общие значения, профиль и настройки таблицы.
2. Затем для загрузки сохраняет план: какие проверки нужны, какие из них обязательны
   и какие настройки действуют. В плане также фиксируются хеш конфигурации,
   версии реализаций и единое время оценки.
3. Обработчик получает измерения и сохраняет фактические ограничения. Это важно,
   если допустимые границы рассчитываются по истории предыдущих загрузок.
4. После выполнения сборщик сверяет результаты с планом и сохраняет общее решение.

Здесь `dataset_id` обозначает набор данных, например таблицу `orders`, а
`scope_id = batch_id` — конкретную загрузку этой таблицы. Как задать правила,
описано в [инструкции по настройке](../config/quality/README.md).

## Статусы

| Уровень | Значения |
| --- | --- |
| Выполнение | PENDING, RUNNING, COMPLETED, SKIPPED, ERROR |
| Результат выполненной проверки | PASS, FAIL, UNKNOWN |
| Итоговая реакция | PASS, WARN, BLOCK |

Эти уровни учитываются отдельно. Например, COMPLETED + UNKNOWN означает,
что функция завершилась нормально, но данных для оценки оказалось недостаточно.
Если проверка пропущена (SKIPPED) или завершилась ошибкой (ERROR), сохраняются
код и описание причины; `CheckResult` при этом не создаётся. Пока есть проверки
в состоянии PENDING или RUNNING, окончательное решение не формируется.

По умолчанию FAIL приводит к BLOCK, а UNKNOWN — к WARN. Настройки позволяют
выбрать WARN или BLOCK, но не превратить проблему в PASS. При объединении
результатов действует приоритет BLOCK > WARN > PASS.

Если обязательный результат отсутствует, итогом будет BLOCK; отсутствие
необязательного результата вызывает WARN. Для двух известных причин пропуска —
недостатка истории (`insufficient_history`) и отсутствия эталона схемы
(`missing_schema`) — реакция задаётся отдельно и по умолчанию равна WARN.
Другие пропуски обязательной проверки приводят к BLOCK.

Сборщик также отклоняет дубли, результаты другой загрузки или колонки и проверки,
которых нет в плане. Наблюдения и ограничения результата должны совпадать
с зафиксированными перед запуском.

Сама функция `evaluate_quality` только объединяет готовые результаты.
Поэтому обработчик дополнительно использует контроль полноты
из `data_quality.execution`.

## Реализованные проверки

| Вид | Когда возвращается PASS |
| --- | --- |
| freshness | Возраст от received_at до времени оценки не больше max_age |
| null_rate | Доля пропусков не больше порога для заданной колонки |
| row_count | Количество строк находится в допустимом диапазоне, включая его границы |
| schema | Ожидаемые поля и типы совпадают; лишние поля разрешены настройкой |

Значение `None` означает, что наблюдение недоступно. При этом 0 строк и пустая
схема — известные значения, которые проверяются обычным образом.
Если ожидаемой колонки нет, её проверка остаётся в плане и возвращает UNKNOWN
для `null_rate`. Проверка `freshness` использует время получения загрузки;
дата заказа внутри строки в этом расчёте не участвует.

## Добавление проверки

Чтобы добавить ещё одну проверку существующего вида, достаточно правила в YAML.
Для нового вида потребуется описать типы наблюдения и ограничения
(`observation` и `constraint`), параметры в `contracts/quality_config.py`,
а также зарегистрировать функцию и подготовку её входов в `data_quality/execution.py`.
Кроме того, обновите сериализацию и расширьте ограничение `kind` в БД отдельной миграцией.

Если меняется смысл проверки, увеличивайте версию реализации. При этом нужно
сохранить возможность завершить планы, созданные для предыдущей версии.

Для каждого вида добавьте тесты PASS, FAIL, UNKNOWN и граничных значений.
Также проверьте повторяемость результата на одинаковых входах и сохранение данных
после преобразования в JSON и обратно. Общий тест UNKNOWN проверяет, что сценарий
есть для каждого зарегистрированного вида.

```sh
python -m pytest tests/data_quality tests/contracts tests/stream_processor -q
```
