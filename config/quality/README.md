# Настройка качества

Настройки разделены на три части: в `defaults.yaml` задаются общие реакции
и повторы, в `profiles/` — переиспользуемые наборы проверок, а в `datasets/` —
правила отдельных таблиц. После изменения файлов перезапустите обработчик,
чтобы он прочитал новую конфигурацию.

Если отдельного файла таблицы нет, применяется `default_profile` из `defaults.yaml`.
Сейчас это профиль `standard`, который проверяет свежесть, количество строк и схему.
Поэтому папка `datasets/` может быть пустой или отсутствовать. Проверки конкретных
колонок нужно добавить в подходящий профиль или в настройки таблицы.

Настройки таблицы имеют приоритет. Если в её файле не указан `profile`, используется
профиль по умолчанию. Если же `default_profile` вообще не задан, таблицы без настроек
отклоняются. Ошибки в существующих файлах также отклоняются, а не скрываются
переходом на общие настройки.

## Настройки таблицы

Настройки применяются в порядке **defaults → один profile → overrides таблицы**.
Раздел `checks` добавляет правила, а `overrides` меняет уже существующие.
При объединении словари дополняются по ключам, а списки заменяются целиком.
Ссылка на неизвестное правило, дубли ключей YAML, неверные типы или параметры
вызывают ошибку при загрузке конфигурации.

Например, для `orders` можно увеличить допустимый возраст загрузки до двух часов
и дополнительно запретить пропуски в `customer_id`:

```yaml
dataset_id: orders
version: 1
profile: standard
overrides:
  freshness:
    params:
      max_age_seconds: 7200
checks:
  customer_id.null_rate:
    kind: null_rate
    column: customer_id
    required: true
    params:
      max_null_rate: 0.0
    on_fail: BLOCK
    on_unknown: WARN
```

Ключ правила должен оставаться стабильным: из него формируется идентификатор
`check_id = dataset_id + "." + ключ`, например `orders.customer_id.null_rate`.
Параметр `required` (по умолчанию `true`) требует получить результат проверки,
а `on_fail` определяет реакцию на обнаруженное нарушение. Колонки задаются явно,
поэтому исчезнувшая из данных колонка не исчезнет из плана проверки.

## Параметры проверок

| kind | params |
| --- | --- |
| freshness | max_age_seconds: целое ≥ 0 |
| null_rate | max_null_rate: от 0 до 1; column обязателен |
| row_count, mode: fixed | min_count и/или max_count: целые ≥ 0 |
| row_count, mode: historical | history_window, min_history, min_ratio, max_ratio |
| schema | fields: список {name, data_type}; allow_extra_fields: false по умолчанию |

Если `fields` не заданы, эталон схемы берётся из предыдущей версии, а при её
отсутствии — из сохранённой текущей. Для первой загрузки такого эталона ещё нет.
При этом явно заданный пустой список `fields` означает требование пустой схемы.

В режиме `historical` границы количества строк рассчитываются по медиане предыдущих
измерений: нижняя равна медиане × `min_ratio`, верхняя — медиане × `max_ratio`.
Обе округляются вниз до целого, а текущая загрузка исключается из истории.
Рассчитанные границы сохраняются перед выполнением проверки.

Если истории недостаточно, проверка получает состояние SKIPPED с причиной
`insufficient_history`. Отсутствие эталона схемы также даёт SKIPPED, но с причиной
`missing_schema`. Настройки `on_insufficient_history` и `on_missing_schema`
определяют реакцию на эти ситуации: WARN или BLOCK.

## Общие настройки и повторы

В `defaults.yaml` задаются профиль по умолчанию, число попыток и реакции на результаты:

```yaml
default_profile: standard
retry:
  max_attempts: 3
  delays_seconds: [5, 15]
policy:
  on_fail: BLOCK
  on_unknown: WARN
```

Параметр `max_attempts` включает первую попытку и допускает значения от 1 до 10.
В примере это один запуск и два повтора с паузами 5 и 15 секунд.
Число пауз должно совпадать с числом повторов; каждая пауза — от 0 до 60 секунд.
Раздел `retry` можно переопределить для конкретной таблицы.
Повторы выполняются при временных технических ошибках. Результат FAIL
и недостаток истории сами по себе не являются поводом для повторного запуска.

## Изменение правил

При изменении правил повышайте `version`. План сохраняет объединённую конфигурацию
и её хеш SHA-256, поэтому последующее редактирование файлов не меняет старую оценку.
Пороги в репозитории служат стартовыми примерами: их нужно согласовать с владельцем
данных. Например, для `orders` разрешено до 50% пропусков даты доставки,
а остальные пороги заданы отдельно по колонкам.

YAML описывает только настройки; исполняемые выражения в нём не поддерживаются.
