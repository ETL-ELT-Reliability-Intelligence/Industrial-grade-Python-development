# События запуска пайплайна

Во всех событиях `orders_ingestion` поле `started_at` берётся из
`context["dag_run"].start_date`: это фактическое начало DAG run, а не logical date
или время запуска отдельной задачи. `PipelineRunReporter.started()` требует
передать его явно, как и методы `finished()` и `failed()`.

`finished_at` и `failed_at` фиксируются часами reporter при отправке сообщения.
Таким образом, длительность охватывает время от начала DAG run до отчёта,
включая ожидание задач и retries. Это не точный момент перехода DAG run в конечное
состояние в метаданных Airflow. `PipelineFinishedEvent.duration_seconds` — обычное
Python-свойство, вычисляемое из временных меток; в JSON/Kafka этого поля нет.

## Ошибки и повторные выполнения

- Сохранены `retries=1` и `retry_delay=1 минута`. Автоматический retry задачи
  относится к тому же DAG run; все отчёты используют его `run_id` и `start_date`.
- `on_retry_callback` не настроен: переход задачи в `up_for_retry` не публикует
  `pipeline.failed`. Ошибка после исчерпания retries (или ошибка без возможности
  retry) вызывает существующий task-level `on_failure_callback`.
- `pipeline.failed` означает ошибку задачи, сообщённую этим callback, а не отдельное
  уведомление о конечном состоянии всего DAG. Смена уровня callback в этот
  рефакторинг не входит.
- При повторном исполнении задачи отчёта возможна повторная публикация. Каждый
  вызов reporter создаёт новый `event_id`; дедупликации между попытками здесь нет.
  Повторная доставка уже созданного сообщения сохраняет его `event_id`.
- Ручная очистка и повторный запуск задач могут дать новые сообщения для прежнего
  `run_id`, в том числе успешное завершение после ранее опубликованной ошибки.
  Reporter всегда использует текущее `dag_run.start_date` из контекста, не хранит
  историю и не восстанавливает начало до ручного сброса DAG run. Для независимого
  жизненного цикла следует создавать новый DAG run с новым `run_id`.

Различия failure/retry callbacks и ограничения ручной смены состояния описаны в
[документации Airflow 2.10.2](https://airflow.apache.org/docs/apache-airflow/2.10.2/administration-and-deployment/logging-monitoring/callbacks.html).

Тесты `tests/pipelines/` проверяют reporter и передачу контекста из DAG с заглушками
декораторов Airflow. Они не запускают scheduler и не проверяют механизм retries
самого Airflow.
