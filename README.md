# Система мониторинга и анализа надёжности ETL/ELT-пайплайнов

Система помогает обнаруживать проблемы с данными, даже когда задачи загрузки и
преобразования завершаются успешно. Например, источник может вернуть только часть
записей: пайплайн останется «зелёным», но рассчитанная выручка окажется заниженной.

Сейчас работает автоматический контур от ingestion через Kafka до проверок качества,
PostgreSQL и дашборда. Он сохраняет исходные данные, проверяет схему, объём, пропуски,
кардинальность, распределения и значения, хранит историю оценок и поддерживает
переоценку. Дополнительно рассчитываются независимые статистические признаки,
выявляются аномалии по правилам и прогнозируется почасовой объём `mock_orders`
при наличии достаточной истории для обучения.

Объединение аномалий в инциденты, поиск первопричин и агент расследования относятся
к дальнейшему развитию. Отдельное приложение `services/demo` показывает инциденты
из подготовленного снимка данных и не подключено к рабочему хранилищу.

## Как работает система

Airflow запускает загрузки, ingestion сохраняет raw-данные в S3 и публикует события
в Kafka. Stream processor читает эти данные, выполняет проверки и сохраняет
результаты. Backend предоставляет их через API, а frontend отображает на дашборде.
В Olist-пайплайне отдельная ветка загружает raw-таблицы в PostgreSQL и строит витрины dbt.

```text
Источник → ingestion → S3 (raw) + Kafka (события)
                         │             │
                         │             └→ stream processor ← S3 (raw)
                         │                       │
                         │                       ▼
                         │              PostgreSQL: качество и аномалии
                         │                       │
                         │                       └→ backend API → дашборд качества
                         ▼
                  PostgreSQL raw → dbt → analytics
```

Результат отдельной проверки — `PASS`, `FAIL` или `UNKNOWN`; политика объединяет
результаты в решение `PASS`, `WARN` или `BLOCK`. Поэтому `FAIL` проверки может
привести к `WARN`, если так настроена политика. Backend читает сохранённые результаты
и не запускает проверки самостоятельно.

## Быстрый запуск

Из корня репозитория запустите сквозное демо. Нужны работающий Docker с Compose
и, если нет готовых CSV, Python 3.11+ с доступной командой `python` для генерации данных.
Первый запуск собирает образы и устанавливает зависимости, поэтому занимает несколько минут.

Windows PowerShell:

```powershell
powershell -File scripts/demo.ps1
```

Linux/macOS:

```bash
bash scripts/demo.sh
```

Скрипт поднимает сервисы и четыре раза запускает DAG `olist_ingestion`: три обычных
месяца формируют историю, а в четвёртом источник отдаёт 40% записей `order_payments`.
Ожидаемый результат: задачи пайплайна завершаются успешно, проверка объёма получает
`FAIL`, а решение о качестве — `WARN`. Откройте дашборд, выберите `order_payments`
и посмотрите результаты последней загрузки.

Если в `data/olist/` есть исходные CSV
[Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce), используются они;
иначе генерируется небольшой набор в том же формате. Нужны четыре файла:
`olist_orders_dataset.csv`, `olist_order_items_dataset.csv`,
`olist_order_payments_dataset.csv` и `olist_customers_dataset.csv`.
Параметр DAG `window` выбирает месяц, а `volume_factors` задаёт долю возвращаемых строк.

| Интерфейс | Адрес |
| --- | --- |
| Дашборд и документация API | http://localhost:8000 и http://localhost:8000/docs |
| Airflow | http://localhost:8080 |
| Kafka UI | http://localhost:8081 |
| PostgreSQL через Adminer | http://localhost:8082 |
| Консоль S3-хранилища | http://localhost:9001 |

Для подключения с хоста Kafka доступна на `localhost:9092`, S3 API — на
`http://localhost:9000`. Контейнеры используют `kafka:19092` и `http://rustfs:9000`.
Демо-скрипты задают `POSTGRES_PORT=5433`, если переменная не установлена;
обычный `docker compose up` использует порт `5432`. Внутри Docker PostgreSQL
всегда доступен как `postgres:5432`.

Команда `docker compose down` останавливает сервисы и сохраняет данные в томах.
Для удаления этих данных используйте `docker compose down -v`.

## Разработка и тестирование

Для локальной работы нужны Python 3.11+ и uv. Зависимости описаны в `pyproject.toml`
и зафиксированы в `uv.lock`. Команды выполняются из корня репозитория:

```bash
uv sync --locked --extra dev --extra storage --extra kafka --extra s3 --extra ml
uv run --no-sync python -m ruff check .
uv run --no-sync python -m pytest
```

Проверки внешних сервисов требуют отдельной настройки: PostgreSQL использует
`TEST_DATABASE_URL`, Kafka — `KAFKA_BOOTSTRAP_SERVERS`. Для браузерных тестов
нужны extra `browser` и установленные браузеры Playwright. Без необходимых
сервисов или зависимостей соответствующие тесты пропускаются; состав проверок CI
описан в [workflow](.github/workflows/ci.yml).
Запуск backend отдельно от демо и настройка БД описаны в
[документации приложения](docs/application/README.md).

### 2 итерация - объединение компонентов в единый автоматизированно работающий пайплайн
На начальном этапе итерации был реализован демонстрационный сценарий, запускаемый командой python -m services.backend.seed: создаются тестовые записи о загрузках, выполняются проверки качества на заданных наблюдениях, рассчитывается решение policy и сохраняются результаты в PostgreSQL. Backend и интерфейс позволяют просматривать сохранённые данные. Автоматическое получение наблюдений из Ingestion и обработка событий Kafka на этом этапе ещё не были подключены.

#### Коновалов И.В.

Соединил ingestion с Kafka и Airflow и проверил цепочку «источник -> ingestion -> Kafka -> потребитель» на реальных сервисах.

**Было.** Ingestion и DAG `orders_ingestion` публиковали события, но сырые данные лежали только в локальной папке, повтор задачи в Airflow создавал новый batch и дублировал события, а Kafka проверялась только вручную.

**Стало.**
1. `S3RawStore` (`services/ingestion/storage.py`): сырые данные и манифесты запусков в S3-совместимом хранилище; переключение `--s3-endpoint` / `S3_ENDPOINT_URL`, локальное хранилище осталось по умолчанию.
2. Идемпотентный запуск: `ingest(source, run_id)` сначала фиксирует события запуска в хранилище, потом публикует; повтор того же `run_id` возвращает тот же batch. У событий есть `dedup_key`, а `contracts/consumer.py` содержит эталонного потребителя с `Deduplicator`.
3. Интеграционный тест ingestion -> Kafka -> consumer (`pytest -m integration`, отдельный job в CI) и запуск всей инфраструктуры через `docker compose`.

**Почему.** Вопросы 13 и 17 из [архитектуры](./docs/ARCHITECTURE.md) (потеря событий, идемпотентность повторной обработки) касались прямо нашего компонента. Unit-тесты с фейками проходили, но полный запуск показал две реальные проблемы: образ MinIO больше не скачивается (заменили на RustFS) и Airflow не мог писать в Kafka из-за одного адреса брокера (добавили два listener'а). Подробности сохранены ниже, в технических заметках этой итерации.

**Не понимаем.**
1. Номер batch считается как «число файлов + 1», два параллельных запуска могут получить один номер. Нужна ли условная запись (put-if-absent) на нашем масштабе?

#### Куриш М.В.
Реализовал сервис `services/stream_processor`, замкнувший первый автоматический контур `ingestion → Kafka → обработчик → PostgreSQL → backend` без ручного seed. Потребитель Kafka с ручным коммитом offset (at-least-once) обрабатывает `dataset.ingested` и события пайплайна: читает сырые данные по `raw_uri`, считает статистики (row_count, null_rate, distinct_count, freshness_seconds), выполняет детерминированные проверки качества (schema, freshness, null_rate, row_count с порогом по медиане истории), сохраняет результаты и решение policy (`PASS`/`WARN`/`BLOCK`), при `FAIL` публикует `data.quality.failed`. Покрыл unit-тестами, интеграционным тестом с PostgreSQL (отдельный job в CI) и документацией (`docs/stream_processor.md`).

#### Технические заметки итерации

##### Почему объектное хранилище — RustFS, а не MinIO

Изначально в `docker-compose.yml` стоял `minio/minio`. При запуске образ не скачивается: Docker Hub отвечает `pull access denied`, зеркало `quay.io/minio/minio` отвечает `unauthorized` (в том числе для закреплённого тега релиза). Причину мы не выясняли, но `docker compose up` падал на этом сервисе, а от него зависит Airflow.

Выбрали `rustfs/rustfs`:

- это S3-совместимый сервер, который скачался и заработал с теми же портами (9000/9001) и учётными данными, что были у MinIO;
- код не привязан к конкретному серверу: `S3RawStore` работает через `boto3` с любым S3 API, поэтому замена потребовала изменить только `docker-compose.yml`;
- мы проверили на нём запись/чтение batch и манифестов запусков, а также DAG в Airflow целиком.

Не проверяли и не сравнивали по производительности, надёжности и лицензии: RustFS — молодой проект, для production выбор стоит пересмотреть (вернуться на MinIO из исходников, взять Garage, SeaweedFS или облачный S3). Имена переменных окружения `S3_*` от сервера не зависят. Логин/пароль `minioadmin` оставлены как локальные dev-значения по умолчанию.

##### Kafka в Docker: два listener'а

Брокер анонсирует два адреса: `kafka:19092` для контейнеров (Airflow) и `localhost:9092` для хоста. Раньше был один адрес `localhost:9092`: клиент в контейнере подключался к bootstrap-серверу, получал в метаданных `localhost:9092` и не мог отправить сообщение (`Kafka delivery failed: timeout`).

**Дополнение.** Сквозное Olist-демо объединяет Airflow, S3, Kafka, загрузку raw-таблиц, dbt и дашборд; сценарий показывает потерю данных при успешном выполнении задач.

Зафиксировал решения по границам Speed/Batch Layer (базовые статистики строятся в Speed, ML-модели drift — в Batch) и владению аномалиями (rule-based детектор у роли №2, ML — у роли №3), устранил дефекты — статистики теперь строятся из профиля батча за один проход вместо двух, история профилей выбирается в SQL с `LIMIT` вместо загрузки всех записей в Python, события о качестве публикуются и при решении `BLOCK` без явных `FAIL`-результатов. Осталась синхронизация документации и полный демо-прогон.
